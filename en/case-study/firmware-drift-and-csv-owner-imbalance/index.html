Case study 01 · base measurement

Six nodes, two firmware versions

Financial services· 6-node Hyper-V· Failover Cluster· NVMe, local storage· Baselinequarter

A production cluster of six Hyper-V nodes had run for three years without a structured review. The administrator reported slow storage with no identifiable cause; the cluster gave no warning at all. The base measurement found two things that reinforced each other: two of the six nodes were on a firmware build with a known NVMe stability regression, and ownership of the Cluster Shared Volumes sat lopsided, so one node carried most of the metadata traffic. Both are invisible in Failover Cluster Manager. Both were repaired within the same cycle.

01

The situation

Six nodes, production workloads, local NVMe storage. The cluster had been delivered three years earlier and patched properly since, but never measured through as a whole. The administrator had a concrete complaint and no evidence: the storage felt slow, in bursts, without anyone able to point at the cause.

That is a common starting point. Failover Cluster Manager showed all nodes healthy, all roles online and no events asking for attention. The validation wizard ran clean. So there was no incident to investigate. There was a suspicion and a cluster that maintained nothing was wrong.

02

The measurement

The collection script ran from the customer management server over WinRM to the six nodes: about fifteen minutes, read-only, nothing installed. From the output two findings emerged that deserved attention on their own and together explained the complaint.

Why this counts

A cluster assumes its nodes are interchangeable. As soon as two nodes behave differently under load than the other four, a failover moves a workload from predictable to unpredictable behaviour, without anything in the log pointing at it. The build involved was known to the vendor for falling NVMe throughput under sustained write load.

Action point

Bring both nodes to the prescribed level, node by node, with the workload drained. Then include the firmware versions in the quarterly measurement, so drift becomes visible before it changes behaviour.

Why this counts

All metadata traffic for a volume runs over the node that coordinates it. If most volumes sit with the same node, that node carries a disproportionate amount of I/O while the rest has capacity to spare. The cluster reports nothing, because there is no fault: everything works, only slower than the hardware can manage. After a failover or a patch round that distribution stays as it is, because nothing puts it back.

Action point

Distribute ownership evenly and include the distribution in the recurring measurement. See also the explanation of lopsided CSV ownership.

The two findings reinforced each other: the node carrying the most metadata traffic was also one of the two nodes on the deviating firmware build. That explains why the complaint came in bursts and was not reproducible: it occurred when the load coincided with the node least able to handle it.

03

What could not be measured

Every CloudLabs report states what stayed out of reach, with the reason. Not because it looks good, but because otherwise a reader does not know how complete the picture is.

  • Management cards of the hosts: reason
  • Switch configuration: outside the scope of the base measurement; covered by module M1
  • Performance history before the measurement window: not retained on the hosts

04

The repair

The repair ran within the same cycle, node by node, with the workload drained each time:

  • The two deviating nodes were brought to the prescribed firmware level.
  • Ownership of the six volumes was distributed evenly across the nodes.
  • Firmware versions per node and the CSV distribution have been included in the recurring measurement, so both stay visible.

What the customer left alone: finding not taken up, with the customer’s reason. That is stated, because an example in which everything is resolved is not an example but an advertisement.

05

The outcome

The complaint that could not be placed for three years had an identifiable cause and an action. More important to the administrator was something else: for the first time he had a document stating what had been checked and found in order, next to what was wrong. That is the part he could pass to his IT manager without questions remaining.

At the next quarterly measurement the firmware level was equal on all six nodes and the CSV distribution still in balance. That gave the second measurement its purpose straight away: not to find something new, but to show that the repair held.

06

Questions

Why does Failover Cluster Manager not warn about firmware drift?

Because Failover Cluster Manager watches the cluster roles and not the firmware of the hosts. A node with an older or newer build is a valid node to the cluster: it accepts roles, keeps its vote and reports healthy.

Nor does the validation wizard compare driver and firmware versions between nodes. Differences only surface when someone puts the versions per node side by side, or when behaviour under load starts to diverge per node.

What is lopsided CSV ownership and why is it a problem?

Every Cluster Shared Volume has a node that coordinates it; all metadata traffic for that volume runs over that node. If most volumes sit on the same node, that node carries a disproportionate amount of I/O while the other nodes stand idle.

The cluster reports nothing, because there is no fault. Everything works, only slower than the hardware can manage.

Does the cluster notice the measurement?

No. The collection script only reads and installs nothing. It runs from the management server over WinRM to the nodes, takes about fifteen minutes, processes no passwords and leaves nothing behind.
