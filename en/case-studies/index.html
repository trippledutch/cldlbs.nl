Case studies

What a measurement finds
in a cluster that is doing fine

Anonymised, because it concerns someone else’s environment. With the measured values included, because without those values it is not a finding but an opinion.

CloudLabs measures Hyper-V, Failover Cluster and Azure Local environments with a read-only PowerShell script and records the result in a findings report. In the examples below four things come back most often: firmware and driver versions that differ per node, Cluster Shared Volume ownership that sits lopsided, quorum and witness configurations that would not survive a second site, and RDMA settings that do not match between host and switch.

None of these four gives a warning in Failover Cluster Manager. All four are visible in a measurement. Each example below names the measured value, the node involved and the moment.

The anonymisation

What we publish and what never

A case study is only usable once you know what has been taken out of it. That is why it stands here and not in a footnote.

What is in it

  • Sector, with the size and shape of the cluster: number of nodes, storage form, number of sites.
  • The findings as they stood in the report, with risk level.
  • The measured value that proves the finding and the value that was required.
  • What could not be measured, with the reason included.
  • What was repaired and what the customer left alone.

What is never in it

  • The name of the organisation and the name of the cluster.
  • Host names, IP addresses, serial numbers and licence data.
  • The exact date. A month is given, or a quarter.
  • Anything by which the environment can be found or reached.
  • A logo or a quote the customer did not give permission for.

Node names have been replaced by NODE01 to NODE06. Where a replaced name appears in a finding, that is stated with the example.

Questions about these examples

What you rightly ask of this

All frequently asked questions hans.vredevoort@cldlbs.com
Why are there no customer names with these case studies?

Because a cluster finding tells where an organisation was vulnerable. Anyone who sees their quorum configuration or a firmware version below the required level in a report does not want that sentence on the internet with their name next to it.

CloudLabs therefore publishes sector, size, environment type and the measured values. No customer name, no cluster name and no address. A reference call is possible: then the customer explains it themselves, to someone who works with a comparable environment.

Are the measured values in these examples real?

Yes. The sector, the size of the cluster, the type of environment, the findings and the outcome come unchanged from the measurement. Only what is traceable to the organisation has been replaced: customer name, cluster name, host names, IP addresses and exact dates.

Where a node name is needed to understand the finding, a replacement name is used. That is stated with the example.

Can I speak to a previous customer?

Yes, on request. We put you in touch with a customer in a comparable environment: the same type of cluster, roughly the same size, preferably the same storage form. That runs through the customer and not around them; they are asked first whether they are willing.

How do I know whether my cluster has the same problems?

You do not know that from an example. That is exactly the point. Firmware drift, lopsided CSV ownership and deviating PFC classes are not visible in Failover Cluster Manager and give no warning. They emerge from a measurement.
